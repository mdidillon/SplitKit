# SplitKit working rules

- `Docs/Specification.md` is the source of truth. Read the relevant sections before changing code.
- Work happens directly on `main` in Marc's working copy `~/Github/SplitKit` (the only clone; nobody else works on the repo). No branches, no pull requests, no worktrees, no extra clones. Make small, focused commits on `main` and push them.
- Never put a revision, version or phase in file names (no `rev2`, `-v3`, `Revision4`, `Phase0-` etc.): milestones are just commits, so overwrite the file and let git history keep the versions. The spec is always `Docs/Specification.md`.
- No folders holding only 1-2 files: put such files in the parent folder instead (e.g. `Docs/` stays flat).
- Leave no scratch, prompt or log files in the repo, in `~` or in `/tmp`; build caches stay in git-ignored `.build/` folders.
- Every task report (and the commit message body for substantial commits) carries the §13 report: exact commands, exit codes, test counts (pass/fail/skip), coverage when applicable, known gaps, and manual checks for Marc. Claim nothing as working without evidence.
- Any deviation from the spec needs a written deviation report and Marc's approval.
- Update `Docs/Traceability.md` with every change that affects a requirement.
- Toolchain (spec §1): local development on Xcode 27.1, Swift 6.4, Swift 6 language mode; deployment target macOS 26 (the dev Mac runs macOS 27.0.1; record both OS versions in reports, never add availability branches). Both manifests start with `// swift-tools-version: 6.2`; no 6.4 tools-version path in P1.
- CI (spec §1): GitHub-hosted `runs-on: xcode-27` preview image; accepts any Xcode 27.x until a final 27.1 is on the image (actions/runner-images#14850), asserting `xcodebuild -version` matches `^Xcode 27(\.|$)` and printing `xcodebuild -version` and `swift --version` into the job summary. Our selector prefers 27.1 (incl. RC) over newer 27.x betas (a deviation from §1's "newest", approved by Marc 17 Oct 2026 and recorded in spec §1 and §11.1). If no 27.x is found CI goes red and Marc decides; never change the toolchain silently.
- Package graph (spec §3): content products depend on `SplitKitContent`, never on the `SplitKit` UI target. No target in `SplitKit/` depends on `SplitKitViews/`.
- Repository layout per spec §2: spikes live in `Spikes/SpikeA-LiveTransfer/` and `Spikes/SpikeB-RealityKit/` and are never a dependency of any package; spike results are recorded in spec §11.1 (no separate ADR files); manual checklists and visual references live directly in `Docs/`.
- Single point of change: every concept has exactly one implementation. Before writing a type, view, helper, style, constant or test utility, search the codebase (`rg`) for an existing one and reuse or extend it; never re-implement the same thing a second time, even slightly differently. Shared view parts live in one place (chrome in `Chrome/`, styling and tokens in `Styles/`); views take their values from `SplitKitTokens` and styles, never hard-coded numbers or colours. Shared test helpers live in `TestSupport.swift`. If two implementations of the same thing exist, merge them in the same task and mention it in the report.
- `Docs/Design.md` is the single source of truth for visual design (tokens and defaults, `.glass`/`.plain` styles, appearance and accessibility, header anatomy and states, typography, view reuse rules, the Larevo reference). The spec must not redefine design elements; it only references Design.md. Treat Design.md as binding input for all view work; values marked **[check]** are provisional until Marc has checked them visually. Any new token, style constant or state look goes into Design.md first.
- Never delete files you did not create in the task.
- If the spec is ambiguous, stop and report instead of guessing.
